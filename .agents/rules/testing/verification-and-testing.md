# 本地验证、测试有效性与交付标准

本文件是项目中本地代码验证、自动化测试质量要求及最终任务交付标准的专项规范，服从根目录 [AGENTS.md](../../../AGENTS.md)。

---

## 1. 本地验证与交付标准

在提交代码、发起 PR 或向用户汇报交付前，必须在本地严格执行完整验证：

### 1.1 按改动类型的针对性门禁分级
验证应与实际改动范围精准匹配，严禁脱离改动实际机械堆砌无关检查：
- **纯文档变更（仅修改 `docs/` 或各级 Markdown 文档）：**
  - 执行 `pnpm check:docs`（校验文档相对链接、标题锚点与 Markdown 表格列数）；
  - 执行 `git diff --check`（排查空白字符与格式冲突）；
  - **无需运行全量单元测试与类型检查**，避免无谓的资源与时间消耗。
- **纯注释与文件头调整（不涉及运行时执行逻辑）：**
  - 执行 `pnpm typecheck`（校验 JSDoc/TSDoc 类型注解合法性）；
  - 执行 `pnpm check:boundaries`（校验手写源码核心文件头规范）；
  - **无需运行全量单元测试套件**。
- **业务代码变更、Bug 修复与架构重构：**
  - 本地优先运行目标模块的针对性测试（如 `pnpm vitest run <test-path>`）；
  - 最终功能交付或发起 PR 合并前，必须在本地运行全量检查命令并确保 100% 通过：
    ```bash
    pnpm check
    ```
    该命令在当前工程中涵盖全量检查项：
    1. **类型检查（`typecheck`）：** 校验服务端与浏览器端的 TypeScript 强类型契约；
    2. **测试套件（`test`）：** 运行所有单元测试与集成测试；
    3. **边界与依赖检查（`check:boundaries`）：** 校验模块依赖方向、realm/kind 白名单与反深层导入约束；
    4. **模块目录检查（`check:catalog`）：** 校验模块注册表与代码目录结构一致性；
    5. **静态资源检查（`check:assets`）：** 校验媒体与配置资源的完整性；
    6. **文档检查（`check:docs`）：** 校验所有文档的相对链接、标题锚点与 Markdown 表格列数匹配。

### 1.2 规范交付报告
交付时必须提供自解释的交付报告，清晰写明：
1. **具体改动（Changed What & Why）：** 变更的业务场景、核心模块与技术原因；
2. **验证结果（Verification Results）：** 本地运行测试与检查的命令与结果证据；
3. **偏差说明（Deviations）：** 若存在与原有预期的微调，如实说明原因；
4. **未决事项（Open Questions）：** 若有需要维护者进一步决策的内容，清晰列出。
每行 diff 均应能追溯到明确需求，**严禁遗留 TODO、临时占位实现或调试输出**。

## 2. 测试有效性（Testing Standards）

测试是系统质量与不变量的生命防线，必须真正验证业务行为而非走过场：

### 2.1 强有效断言与反脆弱
- **强有效断言：** 测试断言必须精确验证状态变更、数据结构与返回值的正确性，严禁使用虚晃一枪的弱断言（如仅检查 `expect(result).toBeDefined()`）；
- **稳定性与独立性：** 测试用例必须具备幂等性与独立性，不依赖用例间的执行先后顺序，能够独立重复运行；
- **反过度 Mock（Anti-Fragile Mocks）：** 核心业务与领域逻辑优先编写针对真实行为的测试，避免对内部私有函数或中间实现细节进行脆弱的深层 Mock。

### 2.2 核心测试覆盖维度
测试套件必须全面覆盖以下场景：
- **核心逻辑与业务规则：** 游戏数值计算、法案流程、时间推进与命令分发；
- **正常路径（Happy Path）：** 标准业务输入下的全流程贯通；
- **异常路径（Error Handling）：** 输入错误、网络超时、资源缺失时的异常处理与安全退出；
- **边界情况（Edge Cases）：** 空集合、极值、越界输入与状态机边界转换；
- **API 与协议契约：** HTTP 端点输入校验、WebSocket 消息包格式与 DTO 序列化；
- **安全防线：** 权限越界拦截、命令防伪与信任边界守卫。

### 2.3 面对测试失败的铁律
当测试执行失败且暴露出真实代码缺陷时：
- **直接修复源码：** 必须在业务源码中彻底修复逻辑缺陷；
- **严禁削弱测试：** **绝对严禁通过删除断言、放宽预期或修改测试用例来伪造“测试通过”**！
