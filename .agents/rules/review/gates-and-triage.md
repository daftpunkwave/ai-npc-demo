# 门禁分级与审查处理策略

本文件是项目中自动化 CI 门禁检查结果分诊、静态扫描告警处理以及审查线程互动的专项规范，服从根目录 [AGENTS.md](../../../AGENTS.md)。

---

## 1. 门禁以仓库实际配置为准

- 严格以仓库实际配置的必需检查（Checks）与审查策略为准，不硬编码任何未经配置的第三方门禁；
- 在自动化流程中，通过应用 CI 事件通知等待门禁结果，避免机械轮询。

---

## 2. 门禁分级与处置策略

面对自动化门禁（CI、静态扫描、代码检查器）报出的问题，实施严格的分级处置：

### 2.1 红线必改项（Zero Tolerance）
无论是由哪个工具、在哪个阶段检出的问题，只要属于以下范畴，**必须 100% 在当前改动中确切修复**，零容忍过关：
1. **真实 Bug：** 逻辑缺陷、状态崩溃、非法空指针、类型契约破坏等；
2. **安全漏洞（Security）：** 注入风险、越权访问、不安全依赖等；
3. **隐私与密钥泄露（Privacy / Secrets）：** 提交了敏感凭据、Token、内部私钥等。

### 2.2 非阻塞告警与误报甄别
对于工具报告的非阻塞合并类告警（如圈复杂度、代码重复率、文档覆盖率、格式风格等），因静态扫描存在误报可能，执行以下处置流程：
1. **先核实真伪：** 结合实际代码运行行为、上下文与架构合理性甄别问题是否属实，若确系误报，记录甄别依据；
2. **属实且可局部解决：** 在当前改动中一并顺手完成最小精准修复；
3. **属实但超纲复杂：** 若问题属实，但改动体量过大、复杂度过高或超出当前任务职责边界而不宜就地扩散修改的，**必须为该问题新建独立的跟踪 Issue**（注明背景、现状与建议修复方向），并在 PR 讨论中附上该 Issue 链接；
4. **严厉禁令（No Silent Drop）：** 绝对严禁既不修复、也不建 Issue 跟踪就静默丢弃真实告警！

---

## 3. 审查意见与审查线程（Review Threads）处理原则

### 3.1 审查意见处理四步法
针对 Reviewer 或维护者提出的审查意见，按标准四步法处理：
1. **核实：** 仔细对照代码与业务场景核验问题真实性；
2. **修复：** 在本地完成最小精准修改；
3. **验证：** 运行本地适用测试与门禁验证修复效果；
4. **回复：** 在对应的审查评论中清晰回复处理结果与技术依据。

### 3.2 审查线程 Resolve 限制
普通评论不等同于审查线程。PR 中的审查线程必须严格满足 [PR 全生命周期规范](../git/pr-lifecycle.md#6-审查线程-resolve-铁律strict-resolve-conditions) 中定义的 3 种法定情形方可点击 Resolve，严禁敷衍过关。
