# 编码审查十二维工程准则

本文件是项目中代码编写、重构自审及同行/机器审查（Code Review）的权威核心准则与重点清单，服从根目录 [AGENTS.md](../../../AGENTS.md)。

---

## 审查总则

所有代码变更在交付或评审时，必须逐条对照以下十二个工程维度及最终交付复核进行严格检查，杜绝浮于表面的形式化审查。

---

## 1. Correctness（正确性）
- **核查范围：** 业务逻辑、条件判断、循环分支、数据转换与计算、状态机转换、返回值、执行顺序、数据流、副作用、持久化、并发行为、不变量（Invariants）、前置与后置条件。
- **评判准则：**
  - 确保实际行为严格符合需求、游戏规则、类型定义与 API 契约；
  - 杜绝逻辑漏洞、非法状态转换、竞态异常与因隐式类型转换导致的计算错误；
  - 确保状态迁移在边界条件下依然具备自洽性。

## 2. Edge Case（边界防御与局部异常）
- **核查范围：** `null`、`undefined`、空集合/空数组、缺失字段、非法输入/未匹配枚举、越界值、`NaN`、Promise rejection、timeout、cancellation 等。
- **评判准则：**
  - 显式防御边界值与异步竞态；
  - **严禁静默失败：** 绝对禁止空的 `catch {}` 块；捕获异常若需向上传播，必须附带上下文诊断信息；
  - 确保发生异常时系统不进入非法或不可恢复状态；
  - 确保各类系统资源（网络连接、文件句柄、定时器、事件监听器）在异常分支下可靠释放，严禁残留僵尸后台任务。

## 3. Security（安全性与信任边界）
- **核查范围：** 信任边界、输入合法性校验、认证（AuthN）、授权（AuthZ）、权限控制、越权访问、注入防护、Path Traversal、敏感数据（Secret / Token / 密码）泄露、过度权限与不安全网络配置。
- **评判准则：**
  - 确保核心安全检查置于服务端信任边界且无法通过任何客户端正常或异常调用路径绕过；
  - **严禁前端安全假象：** 严禁依靠前端校验代替后端的真正安全控制；
  - 严禁在代码、注释或配置文件中硬编码任何敏感凭据；
  - 不得以 fallback、吞错或禁用校验等方式伪造安全成功。

## 4. API Contract（契约一致性）
- **核查范围：** HTTP API、RPC、模块导出、Provider 接口、事件（Event）、WebSocket 消息、数据传输对象（DTO）与 TypeScript 类型契约。
- **评判准则：**
  - 输入输出契约明确、自解释且保持最小化设计；
  - 默认值与空值（`null` vs `undefined`）语义全局一致；
  - 保持向后兼容性，不暴露内部实现细节或私有状态；
  - 不迫使外部调用方依赖内部私有结构。

## 5. Decouple（解耦、单一职责与反副作用）
- **核查范围：** 模块边界、职能划分、单一职责（SRP）、纯函数比例、副作用控制。
- **评判准则：**
  - 遵循“低耦合、高内聚”与“解耦优先于内聚”的原则；
  - 各模块职责保持正交互斥，最小化变更半径；
  - 修改模块 A 不得迫使无关模块 B 被动联动修改；
  - 测试模块 A 不得依赖无关模块 B 的具体实现；
  - 严禁通过“万能对象”或冗余浅层抽象（wrapper hell）掩盖真实的紧耦合。

## 6. Dependency（依赖治理）
- **核查范围：** 模块间依赖关系、包依赖树、第三方库引入与版本隔离。
- **评判准则：**
  - **单向依赖树铁律：** 模块依赖必须保持干净、整洁的单向流动，严禁引入循环依赖或依赖方向混乱；
  - 外部第三方依赖用途必须明确、位于合理的防腐隔离层内；
  - 第三方库的错误处理必须完备；
  - 严禁将第三方特有实现细节或专用类型直接泄漏到核心领域层中。

## 7. Performance（性能与扩展性）
- **核查范围：** 算法时间/空间复杂度、轻数值与状态计算的重复计算/遍历/排序、重复 I/O、SQLite 查询 N+1、渲染循环中的临时对象频繁分配（GC 抖动）、不必要的深拷贝、无界集合与无界缓存。
- **评判准则：**
  - 优先识别并解决对实际运行产生实质影响的性能瓶颈；
  - 避免无上限增长的内存集合与全局缓存（必须有合理的淘汰或生命周期释放策略）；
  - **反过度优化：** 严禁以微小、无测量证据的性能收益为代价牺牲代码正确性、系统稳定性与架构清晰度。

## 8. Resilience（系统级韧性）
- **核查范围：** 网络与模型调用超时（Timeout）、指数退避重试（Backoff Retry）、请求取消（AbortController）、并发并发度控制、故障隔离、优雅降级、防雪崩及高频交互保护（如防抖/节流、请求竞态覆盖）。
- **评判准则：**
  - 外部服务调用必须具备兜底超时控制与取消机制；
  - 确保局部依赖故障或网络抖动不会扩散演变为系统级级联崩溃；
  - 在依赖暂时不可用时，系统应具备可预期的降级表现。

## 9. Maintainability（可维护性）
- **核查范围：** 认知复杂度（Cognitive Complexity）、过长函数、过大类/文件、职责混合、隐式状态与魔法值。
- **评判准则：**
  - 核心评判判准：修改一个功能时，是否迫使开发者需要理解或修改大量无关代码？
  - 消除隐式上下文传递与未命名的魔法数字/字符串常量；
  - 优先降低开发者的认知负荷，严禁为了形式上的整洁或教条式的 DRY（Don't Repeat Yourself）进行机械抽象。

## 10. Naming（意图导向命名）
- **核查范围：** 目录、文件、类、接口、类型、函数、变量、配置项等所有标识符。
- **评判准则：**
  - 严格遵循意图导向命名，精准反映真实领域职责与抽象层级；
  - 严格遵循命名黑名单与高危词管控规则（详见 [命名规范与文件头规范](../conventions/naming-and-headers.md)）；
  - 严禁临时性、主观性命名。

## 11. Documentation（文档与注释）
- **核查范围：** 手写源码文件头（File Header）、JSDoc/TSDoc 注释、技术文档、变更说明。
- **评判准则：**
  - 检查注释准确性与实际实现的一致性，及时清除废弃陈旧注释；
  - 注释仅用于解释“Why”（设计权衡、特殊约束与非直观边界），不逐行翻译“What”；
  - 核心源码必须具备规范中文文件头（详见 [命名规范与文件头规范](../conventions/naming-and-headers.md)）；
  - 严禁机械添加无信息量的废话注释。

## 12. Testing（测试有效性）
- **核查范围：** 单元测试、集成测试、测试断言质量、测试用例独立性。
- **评判准则：**
  - 测试必须真正验证业务行为而非内部实现细节；
  - 具备强有效断言，杜绝无断言或弱断言（如仅断言 `defined`）；
  - 测试必须稳定、独立、可重复，不依赖执行顺序，杜绝脆弱 Mock；
  - **反削弱测试：** 当测试暴露出代码真实缺陷时，必须直接修复业务源码，严禁通过修改或削弱测试断言掩盖问题。

## 13. Final Verification（最终整体交付复核）
- **核查范围：** 整体交付质量与自动化检查门禁。
- **评判准则：**
  - 全部编码与审查修复完成后，在本地依据变更类型严格执行适用的检查门禁（详见 [本地验证与门禁分级](../testing/verification-and-testing.md#11-按改动类型的针对性门禁分级)）：
    - **业务代码变更、Bug 修复与重构：** 必须在本地运行全量检查并 100% 干净通过：
      ```bash
      pnpm check
      ```
      涵盖类型检查 `typecheck`、测试套件 `test`、边界检查 `check:boundaries`、模块目录检查 `check:catalog`、资源检查 `check:assets` 及文档检查 `check:docs`；
    - **纯文档变更（仅修改 `docs/` 或 Markdown 文档）：** 执行 `pnpm check:docs` 与 `git diff --check`，免跑全量测试套件；
    - **纯注释与文件头调整（无运行时代码改动）：** 执行 `pnpm typecheck` 与 `pnpm check:boundaries`，免跑全量测试套件；
  - 确保当前变更适用的所有检查门禁 100% 干净通过，方可提交或发起合并。
