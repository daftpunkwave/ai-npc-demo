# 命名规范、代码注释与核心文件头规范

本文件是项目中代码标识符命名、代码注释风格、手写源码核心文件头（File Header）书写以及 Git 跟踪内容客观性的专项规范，服从根目录 [AGENTS.md](../../../AGENTS.md)。

---

## 1. 意图导向命名（Naming）

### 1.1 核心命名原则
- **意图明确：** 目录、文件、类、接口、类型、函数、方法、参数与变量按边界、职责及业务含义中立命名，精准反映真实职责、业务含义与抽象层级，并与最终代码结构保持一致；
- **适配器命名：** 适配器保留真实技术实现名，不因目录措辞重命名冻结能力 ID；
- **语言惯例：** 代码标识符遵循 TypeScript/JavaScript 语言生态通用命名惯例（类与类型采用 PascalCase，变量与函数采用 camelCase，常量采用 UPPER_SNAKE_CASE）。

### 1.2 命名绝对黑名单
严禁使用主观、模糊或临时性质的命名，包括但不限于：
- `temp`、`tmp`
- `new_logic`
- `quick_fix`
- `helper2`
- `MyManager`
- `DataHandler`
- `CommonUtil`

### 1.3 高危泛化词管控与上下文界定
谨慎使用语义宽泛的通用词汇，除非结合上下文能清晰明确地表达目录或组件职责：
- **高危泛化词列表：**
  - `utils`、`helpers`、`common`、`shared`
  - `manager`、`service`、`handler`、`processor`、`controller`
  - `core`、`base`、`misc`、`data`、`logic`
- **代码标识符与顶层模块：** 类、接口、函数、变量及独立顶层包命名时，避免单独使用上述泛化词，必须具备明确、真实的业务领域限定（例如使用 `PerceptionEventProcessor`，而非单用 `Processor`；使用 `CommandGateway`，而非单用 `Manager`）；
- **嵌套目录的上下文包容：** 项目采用分层嵌套目录结构（如 `<module>/<area>/core` 或 `<package>/src/data`），若其父级目录路径已具备清晰的业务领域限定，使用 `core`、`data` 等子目录是完全合理且可接受的；但仍应保持审慎，确保该目录职责单一自解，严禁将其作为无序堆砌杂项逻辑的“垃圾桶”。

## 2. 注释与代码自解释规范（Comments）

### 2.1 语言与表达
- **默认全中文：** 注释、文件头、技术说明与开发交流默认使用中文，保留英文专有名词（如 deadlock、WebSocket、Actor）；
- **面向玩家的文本与 prompt：** 面向玩家的文案和模型 prompt 统一放置在内容包或专用资源文件中。

### 2.2 自解释代码
- **代码直接表达 What：** 变量、函数、类与类型命名及结构设计必须清晰直白地表达“做什么”（What）；
- **注释专门解释 Why：** 注释仅用于解释“为什么”（设计权衡、特殊上下文约束、非直观契约、非常规边界处理）；
- **反机械复述：** 严禁逐行复述代码执行逻辑，不机械给每个函数添加无价值的注释。

### 2.3 遵循语言原生规范
- **TypeScript / JavaScript：** 严格遵循 JSDoc / TSDoc 格式规范（如 `/** ... */`）；
- **Shell 脚本：** 使用 `#` 注释；
- **SQL 文件：** 使用 `--` 注释；
- **结构化元数据：** 在必要时准确标注 `@param`、`@returns`、`@throws`、`@template` 等原生标签。

## 3. 核心文件头规范（File Header Conventions）

每个手写源码文件（核心业务领域、架构核心、公共基建、测试、脚本、迁移与源码配置）必须包含符合语言原生规范的中文文件头（保留英文专有名词），清晰界定以下三项：

1. **核心职责（Responsibilities）：** 文件承载的功能边界与核心任务；
2. **交互契约（Contracts）：** 依赖能力、输入输出契约与环境假设；
3. **约束与禁忌（Constraints）：** 依赖禁忌、副作用限制与禁止事项。

### 3.1 TypeScript 文件头示例
```ts
/**
 * 核心职责：在分发到已绑定的 authority port 前校验命令信封。
 * 交互契约：依赖命令 schema 与注入的授权契约。
 * 约束与禁忌：禁止执行游戏规则或持久化世界状态。
 */
```

### 3.2 独立可读铁律
- **脱离文档可读：** 文件头只解释代码本身，外部开发者脱离开发文档也应能清晰理解该文件的职责和约束；
- **严禁引用内部文档与计划：** **严禁在文件头中引用内部开发文档路径、文档链接或构建阶段编号**；
- 具体 header 覆盖范围与例外规则统一见 [技术栈](../../../docs/delivery/tech-stack.md)。

## 4. 客观性与事实性铁律（Git 跟踪内容约束）

所有受 Git 跟踪的文件、注释与文档必须遵守以下客观性原则：
1. **客观中立：** 使用朴素、准确的表述；事实陈述必须可核对，严禁夸大、臆造、情绪化表达和空话；
2. **如实陈述现状：** 代码注释和实现说明只陈述当前可核对的事实与现行有效契约。已交付范围和实测结论必须有确凿证据；
3. **隔离未跟踪内容：** 除声明本地指令文件 `AGENTS.local.md` 这一技术机制外，严禁在受 Git 跟踪的内容中提及任何其他未被 Git 跟踪的本地私有文件或目录（如外部协作者不可见的本地私有路径）。
