# Issue 创建、管理与维护规范

本文件是项目中 Issue 提单策略、分诊分类、模板执行、侧边栏配置及全生命周期维护的专项执行规范，服从根目录 [AGENTS.md](../../../AGENTS.md)。

---

## 1. 强制阅读并严格遵循 Issue 模板

在提出任何 Issue 之前，提单人（包括 AI Coding Agent）**必须完整阅读仓库提供的官方 Issue 模板**：
- **模板文件路径：** [`.github/ISSUE_TEMPLATE/general-issue.md`](../../../.github/ISSUE_TEMPLATE/general-issue.md)

提单时必须严格基于客观事实和实际代码基线，结合模板结构化栏目组织正文，杜绝信息缺失、臆断推测与空泛陈述。

---

## 2. 前置按需建单策略（When to Open an Issue）

提单视具体任务性质而定，采取按需建单策略，避免形式主义与冗余建单：

| 任务场景 | 建单策略 | 判定依据与说明 |
|---|---|---|
| **Bug 修复** | **优先开单** | 出现错误行为、逻辑缺陷或状态异常时，优先开 Issue 记录基线与复现证据；若 Bug 极小且修复逻辑极其直观，可直接提 PR 免去冗余建单。 |
| **大型或高风险变更** | **必须开单** | 任何改动体量过大、影响面广、涉及跨模块重构或复杂架构设计的任务，**必须优先开 Issue** 进行充分对齐与排期。 |
| **常规重构与日常任务** | **按需开单** | 功能新增、常规重构、文档更新或 CI/CD 优化等任务并非必须开单，可由直接关联的任务分支推进。 |

## 3. Issue 侧边栏（Sidebar）配置铁律

提单时必须充分利用 Issue 页面右侧（Sidebar）配置栏，明确分工、各司其职。右侧配置与正文描述严格分离，不重复冗余。

### 3.1 Type 必选（严格三选一）
必须指定以下类型之一，严禁留空：
- `Bug`：系统漏洞、逻辑缺陷、异常崩溃、契约违背或破坏不变量的故障；
- `Feature`：建议的新功能、新能力提案、新业务规则或需求想法；
- `Task`：除上述两类外的所有具体工作项（架构重构、测试补充、文档维护、工程化与 CI/CD 优化等）。

> [!CAUTION]
> **严厉禁令：`bug`、`feature`、`task` 严禁出现在 Labels 中！** 类型必须且仅能通过右侧原生的 `Type` 属性标记。

### 3.2 Fields 结构化字段
- **Priority（必选）：** 统一通过右侧 `Fields.Priority` 下拉指定 P0 ~ P4 其中一个重要度等级，严禁作为 Labels 维护：
  - `P0`（紧急阻断）：核心业务闭环阻塞、主干构建发布中断或关键数据正在不可逆损毁，缺少可行临时绕过方案，须立即处理；
  - `P1`（严重缺陷）：核心流程在常规场景下严重受损，或近期关键交付面临明确阻塞，但仍可通过临时降级维持运行；
  - `P2`（正常排期）：非核心流程出现确定的功能或性能退化，日常工作需要额外规避步骤，核心业务仍正常运转；
  - `P3`（轻微瑕疵）：局限于界面展示、文案说明、交互提示或易用性瑕疵，不影响功能逻辑闭环；
  - `P4`（择期优化）：预防性重构、降低维护成本、消除技术债务或技术调研。
- **Effort（选填/推荐）：** 统一通过右侧 `Fields.Effort` 评估完成该 Issue 所需的相对工作量与复杂度，辅助排期。
- **Start / Target date（选填）：** 按需规划工作起止时间。

### 3.3 Labels 补充维度
- **置信度标签（必打）：** 根据支持核心结论的实证程度打标：
  - `confidence/high`：核心结论具备直接、可独立复核的客观证据（稳定复现步骤、失败断言、明确代码与规范证据）；
  - `confidence/medium`：日志或调用链路支持核心判断，但触发边界、代码实际可达性或影响范围仍待进一步验证；
  - `confidence/low`：仅有初步排查线索（偶发异常、静态扫描提示），现有信息不足以支撑结论，需补充实证。
- **领域标签（必打）：** 至少打一个关联度最大、最核心的领域标签（如 `realm/server`、`area/agent` 等）。
- **证据与特性标签（选打）：** 如 `evidence/reproduced`、`evidence/test-failure`、`evidence/static-analysis`、`performance`、`security` 等。
- **禁止项：** 严禁包含 `bug`、`feature`、`task`，严禁包含 `P0` ~ `P4`。

### 3.4 Relationships 关系追溯（选填）
存在关联时在右侧配置，独立原子任务留空：
- 阻塞关系：`Blocks` / `Blocked by`
- 层级关系：`Parent` / `Sub-issue`
- 上下文关联：`Relates to`

## 4. 标题与正文规范（对齐 Issue 模板）

### 4.1 标题格式建议
推荐格式：`<type>(<scope>): <客观可判定的现象或诉求>`，其中 `<type>` 与右侧 Type 保持意图对应（如 `fix` 对应 Bug，`feat` 对应 Feature，`refactor`/`chore`/`docs`/`test` 对应 Task）。
- 示例：`fix(clock): 暂停后游戏时间仍推进一个 tick`
- 示例：`feat(console): 在研究视图新增决策耗时分布图`
- 示例：`refactor(authority): 拆分超长的命令网关校验逻辑`

### 4.2 正文栏目与格式原则
正文遵循 [Issue 模板](../../../.github/ISSUE_TEMPLATE/general-issue.md) 组织，优先级与置信度由右侧承载，正文聚焦事实证据。**格式水无定势，绝非僵化固定，提单人必须结合实际情况动态调整**：
- **标题禁止携带后缀：** 栏目标题后严禁携带任何「（选填）」、「（建议填写）」等后缀括号内容，提示信息统一作为模板内部注释；
- **无关联项时不写标题：** 若本次 Issue 无关联项或外部依赖，直接不写「相关记录与其他信息补充」节标题与内容；
- **直观问题按需省略：** 逻辑直观、轻量简单的问题可按需省略「复现/证据/设计说明」、「影响范围」、「修复建议」等选填小节；
- **核心建议栏目：**
  1. **Issue 信息：**
     - **代码基线：** 明确给出发现问题或开展任务时的 Git Commit SHA 或正式版本号；涉及性能回归时补充对照基线；
     - **证据类型：** 标明证据支撑（如 `evidence/reproduced`、`evidence/test-failure`、`evidence/ci-failure`）；
     - **架构领域与职能领域：** 正文中**必须完整列出所有涉及的架构边界与职能模块**（如 `realm/server, realm/contracts`），右侧 Labels 仅打主关联标签；
     - **Issue 来源：** 标明发现渠道（PR 审查、本地开发、CI 运行等）及引入点 Commit SHA。
  2. **问题与需求概览（What & Why）：** 简要说明背景、触发条件或业务场景，明确陈述核心目标。
  3. **实际结果 / 现状：** 客观描述观测到的异常现象、报错日志或系统现状，**明确区分客观事实与主观推断**。
  4. **预期结果 / 目标：** 明确系统应有的正确行为、状态机不变量或交付验收标准。
  5. **复现/证据/设计说明（选填）：** 提供最小稳定复现步骤、错误日志上下文或技术方案草案。
  6. **影响范围（选填）：** 明确受影响的模块、调用方、数据资产、发生频率及临时绕过方案。
  7. **修复/实现建议与测试（选填）：** 说明拟改动代码范围与建议补充的自动化测试用例。
  8. **自审清单核对（选填）：** 提交前逐项核实模板底部的自审清单项。

## 5. Issue 全生命周期维护与角色协同

Issue 不是一次性丢弃的静态文本，而是贯穿问题生命周期的跟踪中枢：

### 5.1 提单人职责（Issue Author）
- 基于客观证据提单，提供确切基线与复现线索；
- 具备侧边栏权限时，必须配置好右侧 `Type`、`Fields.Priority` 与 `Labels`；
- 无编辑权限的外部提单者，在正文末尾注明建议，由维护者代为同步配置。

### 5.2 维护者分诊（Triage）
- 审查 Issue 内容完整性与实证有效性；
- 核实并调整优先级（`Fields.Priority`）与置信度（`Labels.confidence`）；
- 若描述模糊或缺少基线，及时要求补充信息；确认有效后纳入开发排期或指派责任人。

### 5.3 解决人职责（Assignee / Solving Agent）
- **开工前复核：** 在动手写代码前，必须复核 Issue 中的代码基线、复现证据与改动范围，在评论区记录复核结论；
- **排查进展同步：** 发现新线索或定位到深层原因时，在评论区及时追加事实记录，严禁静默篡改正文已记录的初始事实；
- **PR 显式关联：** 提交关联修复 PR 时，在 PR 正文中通过官方关键字显式关联（如 `Fixes #xxx`、`Closes #xxx`），形成双向溯源链路。

### 5.4 关闭与归档准则（Closing Standards）
仅在严格满足以下两类情形之一时，才允许关闭 Issue：
1. **确切修复并合并通过：** 关联的修复 PR 已按授权 Squash 合并入主干，且所有自动化检查通过；
2. **确凿证实为误报或无需处理：** 经严谨核对证实属于工具误报、重复提交（注明 Duplicate of #xxx）或已被其它变更涵盖，并在评论区详细回复技术说明与复核证据。

严禁在未修复、未复核、未给出技术结论的情况下随意、草率关闭 Issue！
