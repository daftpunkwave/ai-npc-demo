# Git 分支与 Pull Request 全生命周期规范

本文件是项目中 Git 分支管理、Pull Request（PR）创建、模板遵循、审查流转与合并全生命周期的专项执行规范，服从根目录 [AGENTS.md](../../../AGENTS.md)。

---

## 1. 分支与严格授权铁律

- **默认分支保护：** `main` 是默认保护分支，变更必须通过 PR 进入主干，严禁直接向 `main` 提交或推送代码；
- **严格授权原则：** 提交、推送、创建 PR 与合并必须获得本次任务的明确授权，严禁继承历史任务的授权；
- **独立任务分支：**
  - 从最新的 `main` 分支检出独立任务分支；
  - 遇到工作区存在已有未提交工作时予以保留，严禁使用重置（`git reset --hard`）或强推清理工作区；
  - 分支命名严格遵循 kebab-case 格式：`<type>/<kebab-case-description>`（例如 `feat/combat-loop`、`fix/pathfinding-overflow`）；
- **提交原子性：** 一次提交只处理一个逻辑变更；若属于构建计划中的开发步骤，按构建计划分步提交。

---

## 2. 强制阅读并严格遵循 PR 模板

创建 Pull Request 时，作者（包括 AI Coding Agent）**必须完整阅读仓库提供的官方 PR 模板**：
- **模板文件路径：** [`.github/PULL_REQUEST_TEMPLATE/pull_request_template.md`](../../../.github/PULL_REQUEST_TEMPLATE/pull_request_template.md)

### 2.1 PR 标题规范
PR 标题遵循 Conventional Commits 格式，用动词开头的具体功能概括改动：
- 格式：`<type>(<scope>): <动词开头的概括描述>`
- 示例：`fix(authority): 拆分命令网关中合并的属性行` 或 `feat(agent): 新增回合超时状态机守卫`。

### 2.2 PR 正文核心栏目（按模板结构组织）
PR 正文必须做到对外独立可读、聚焦代码与 Diff 视角（Changed What & Why），严格覆盖以下栏目：
1. **关联 Issue / PR：** 明确关联本次 PR 解决或相关的 Issue（例如 `Fixes #123`、`Relates to #100`）；若无关联 Issue 则如实注明；
2. **改动概述（What）：** 简要概括涉及的业务场景与核心交付目标，说明代码改动了什么；
3. **改动原因（Why）：** 阐明修改的技术原因、既有缺陷、边界漏洞、缺少能力或重构背景；
4. **改动方案（How，复杂改动必填）：** 聚焦代码视角，说明采用了什么技术方案、关键设计权衡及涉及的核心模块；
5. **测试与验证：** 给出本地执行的客观证据，包括执行命令（如 `pnpm check`）、测试集通过数及门禁状态；
6. **兼容性与影响说明（强制项）：** **必须明确说明是否存在破坏性变更（Breaking Changes）**、对外 API 或契约变动、状态迁移或运行时依赖影响；若确认无破坏性影响，**亦必须明确注明“无破坏性变更”及技术理由**；
7. **审阅要点（Note for Reviewer，选填）：** 提示审阅者重点关注的核心模块、非直观设计或特殊上下文约束；
8. **PR 提交自审清单：** 提交前逐项核对代码清洁、本地验证、独立自解与契约守卫。

### 2.3 PR 侧边栏与 Labels
PR 不包含 GitHub 原生的 Fields 结构化字段，其侧边栏不做特定要求；建议最少打一个 Label 以表达主要任务（如核心领域 `realm/*`、`area/*` 或任务类别）。

## 3. 端到端 PR 负责制（End-to-End Ownership）

一旦创建或接管 PR，负责人必须端到端持续跟进，直至其完全达到可合并标准：
1. 远端所有必需 CI 与质量门禁全部通过；
2. 所有人工作业与机器审查（Reviewer）意见均按规范闭环处理；
3. 所有可 Resolve 的审查线程全部合规 Resolve。

---

## 4. 推送前自审与检查等待铁律

### 4.1 Push 前强制自审与针对性验证
每次 `git commit` 或 `git push` 前，必须在本地依次完成：
1. **代码自审：** 对比 diff 自查每一行变更，确保无多余修改与残留调试代码（清除 `console.log` 等）；
2. **针对性门禁与测试验证：** 根据改动类型运行并确保通过当前适用的检查：
   - **纯文档变更（Markdown 文件）：** 仅需运行 `pnpm check:docs` 检验链接、锚点与表格，核对 `git diff --check`，无需跑全量单元测试；
   - **纯代码注释与格式变更：** 仅需运行 `pnpm typecheck` 与 `pnpm check:boundaries`（校验注释文件头完整性），无需跑全量单元测试；
   - **涉及代码逻辑、功能修复与架构重构：** 运行目标模块测试套件，在最终交付合并前运行全量门禁（`pnpm check`）。
3. **注释与文档同步：** 同步更新变更涉及的代码注释与手写源码文件头。
严禁未经针对性自审与验证频繁盲目 Push。

### 4.2 检查等待与严禁中途抢跑
- **推送后等待机制：** 执行 Push 后，通过应用 CI 通知等待远端所有必需 CI 门禁与已触发的 Reviewer 运行完毕；
- **严禁抢跑禁令：** 在所有必需 CI 与 Reviewer 完成当前轮次前，**绝对禁止再次 Push**，避免强行中断正在进行的审查与造成重复返工。

---

## 5. 问题提取与统筹修复流程

当本轮所有 CI 与审查执行完毕后，执行双渠道提取与统筹修复：

### 5.1 双渠道全量问题提取
必须同时完整读取两个渠道的问题，不遗漏任何线索：
- **渠道 A — PR 评论与内联评论：** 完整读取所有总评、行内评论，特别注意提取并修复工具折叠在 Diff 范围外（如 Outside diff range comments）的问题；
- **渠道 B — 失败 CI 的具体报错日志：** 逐一读取所有失败 Check 的详细日志输出以定位具体报错根因。

### 5.2 统筹修复与批量 Push
1. **集中修复：** 在本地集中修复本轮提取的所有问题；
2. **完整复核：** 完成本地自审与针对性门禁/测试验证（纯文档跑 `check:docs`，代码改动跑适用门禁与测试）；
3. **一次性推送：** 将修复批量提交并一次性 Push 到该 PR；
4. **重新进入等待：** 重新等待新一轮 CI 与审查反馈，循环往复直至完全达标。

---

## 6. 审查线程 Resolve 铁律（Strict Resolve Conditions）

PR 中所有可 Resolve 的审查线程（Review Threads / 内联评论）必须全部合规 Resolve 方可合并分支；普通评论不等同于审查线程，须先核实、修复并回复。

### 6.1 法定 Resolve 条件（严格三选一）
仅在严格满足以下 3 种法定情形之一时，才允许对审查线程点击 Resolve：
1. **真实问题且已确切修复：** 审查线程指出的问题真实存在，已在本地完成代码修复并通过测试验证；
2. **经严谨甄别确认为误报（False Positive）：** 已结合实际代码逻辑、类型契约与运行上下文仔细核查，确凿证明属于工具或审查误报；
3. **超纲有价值问题且已创建新 Issue：** 审查线程指出的问题真实有价值，但因体量过大、过于复杂或超出当前 PR 边界而不宜就地修改，且**已经为其成功创建了新的独立跟踪 Issue**（严禁未建 Issue 先点 Resolve）。

### 6.2 严厉禁令
除上述 3 种情形外，任何情况下均严禁点击 Resolve！绝不允许出现“既不修复、也未确认为误报、更未建新 Issue 就直接 Resolve 敷衍过关”的行为。

---

## 7. Squash 合并与提交信息保留规则

必需检查和审查通过后，仅允许按授权使用 squash merge，严禁使用 merge commit 和 rebase merge；分支清理另按授权执行。

### 7.1 合并标题要求
合并标题必须使用清晰概括本次改动的 PR 标题，末尾追加 `(#PR编号)`，已有后缀不重复添加。

### 7.2 合并正文完整保留
- 按 PR 中提交的先后顺序，逐条保留每个 commit 的完整标题、正文与 trailers；
- 严禁改写、严禁摘要、严禁省略；
- 可加列表分隔，但不得改动原始信息内容；只有一个 commit 时同样保留其完整信息。

### 7.3 合并前终审
合并前以最终 PR head 核对提交清单和正文，避免遗漏最后一次推送；不得用另写的 PR 摘要替代 commit 信息历史。squash 在主干生成一个新 commit，保留完整的提交信息历史。
