# 架构设计与核心工程铁律

本文件是项目中系统架构设计、核心编码实现、安全防线与工程治理的强制铁律，服从根目录 [AGENTS.md](../../../AGENTS.md)。

---

## 1. 核心工程铁律与修复总则

### 1.1 实证判断基准
严格以实际代码、实际运行时行为、依赖关系和实际契约为依据进行工程判断；严禁仅凭代码表象、个人主观偏好或脱离具体上下文的教条式“最佳实践”臆断问题。

### 1.2 问题四步确认法
每发现、排查或处理一个问题，必须依次严格确认以下四要素：
1. **真实性：** 问题是否确凿存在？
2. **实际影响：** 是否存在实质性的功能破坏、稳定性劣化或合理风险？
3. **预期契约：** 正确的预期行为和输出契约是什么？
4. **定位根因：** 最合适、最根本的修复位置在哪里？

### 1.3 最小精准修复与反机械堆砌
- **默认最小精准原则：** 默认必须严格遵守最小精准修改原则，优先执行局部、明确、最小且完整的修复，除非本次任务明确要求进行大型重构或大范围系统改动；
- **保护合理边界：** 保持既有正确行为、合理公开契约与模块边界，严禁随意扩散修改与当前任务无关的业务行为；
- **反机械堆砌：** 严禁为了迎合审查或指标而机械堆砌冗余代码，包括但不限于：
  - 不必要的防御性条件分支；
  - 冗余且无意义的异常捕获包装；
  - 过度抽象与空壳接口；
  - 盲目缓存与盲目重试；
  - 废话注释与脆弱的 Mock 测试。

### 1.4 零推测原则（No Speculation / Zero Hallucination）
- 严禁基于主观猜测生成不可靠的 API、不确定版本的第三方依赖或虚构包名；
- 遇到架构未明确、依赖版本模糊或接口定义存疑时，必须立即停止推断，严格按顺序排查：
  1. 检索本地既有源码、锁文件与配置文件；
  2. 检索官方确切文档；
  3. 主动向用户寻求澄清与确认。

### 1.5 零残留交付（Zero Artifact Left Behind）
交付或提交代码前必须彻底清除一切临时产物：
- 临时调试输出（`console.log`、`debugger` 等）；
- 被注释掉的废弃陈旧代码块；
- 未投入生产的临时 Mock/Stub 数据；
- 遗留的 `TODO`、`FIXME` 标记。

## 2. 架构与安全边界

### 2.1 解耦优先于内聚（全职能插件化）
- **全职能插件化：** 不仅限于记忆（memory），整个系统保持全职能插件化；
- **宿主职责纯粹：** 宿主只保留装配、生命周期、契约校验、安全/事务守卫和唯一管线协调；
- **显式 Provider 装配：** 游戏规则、认知策略、平台功能、传输适配和 UI 由显式 provider 装配；职责与状态所有权遵守 [模块边界](../../../docs/architecture/modules.md)，目录布局遵守 [代码目录](../../../docs/architecture/code-structure.md)。

### 2.2 单一职责与物理隔离（SRP）
- **单一职责：** 单个文件仅承载单一明确职责；若单文件内包含两个不同业务领域或上下文的逻辑，无论行数多寡必须物理拆分；
- **反转发层（No passthrough / wrapper hell）：** 拆分必须基于自然业务边界，严禁制造无实质逻辑的浅层转发壳；
- **源文件体积建议：** 单个源文件建议不超过 500 行；超过时按明确职责拆分文件，严禁强行扩大模块边界。

### 2.3 依赖倒置与可测试性（DIP）
- **依赖注入：** 核心业务逻辑必须通过显式参数或依赖注入（DI）接收外部依赖（如宿主注入的 `HostServices`）；
- **严禁不可控副作用：** 严禁在核心算法内部直接实例化不可 Mock 的全局单例、直接调用 `Date.now()`、`Math.random()`、`crypto.randomUUID()`、隐式读取 `process.env` 或触发不可控外部副作用。

### 2.4 网络与端口白名单
- **严格本地监听：** 系统仅监听本地回环地址 `127.0.0.1:5173` 与 `127.0.0.1:3000`：
  - `5173`：提供玩家前端界面与必要游戏设置；
  - `3000`：提供服务端 API 和 `/console` 控制台（三方势力运营、模型挂载、观测、评估、调试）；
- **双端权限与端口硬约束：** 二者严格遵守 [双端权限](../../../docs/architecture/two-endpoints.md)；**端口一旦被占用即直接报错退出，严禁随意换端口**。

### 2.5 安全守卫与信任边界
- **命令与事务闭环：** 不绕过命令网关、事务提交与授权投影；
- **模型输出不可信：** 模型输出绝不充当既定事实，必须经过系统检验；决策（decision）与言语（speech）严格隔离；
- **契约边界：** 记忆版本、实验隔离、公平对照及密钥边界严格遵守 [范围与不变量](../../../docs/00-scope-and-invariants.md)；
- **服务端信任边界：** 安全控制必须位于服务端/核心信任边界，且无法通过正常或异常调用路径绕过；**严禁使用前端校验代替真正的后端核心安全控制**；严禁用 fallback、吞错或禁用校验等手段伪造成功。

## 3. 依赖治理与单向流动

### 3.1 单向依赖树铁律
模块之间的依赖关系必须干净、整洁、严格保持单向流动，绝对禁止引入循环依赖或依赖方向混乱。

### 3.2 依赖与 Import 隔离
- **三层分开校验：** 源码 import、包依赖（package.json dependencies）与运行时 requires 分开校验，严格遵守 [技术栈](../../../docs/delivery/tech-stack.md) 的 realm/kind 白名单；
- **严禁深层导入：** 不得跨模块导入未导出实现，禁止深层导入（如 `@ai-npc/xxx/src/...` 形式）；
- **无共享可变状态：** 模块间严禁共享可变状态；环境与 I/O 必须通过规定的注入和适配器边界流动；
- **外部依赖防腐：** 外部依赖用途必须明确、位于合理防腐隔离层内，第三方实现与专用类型绝不泄漏到核心领域层。
