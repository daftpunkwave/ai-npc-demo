# 文档编写与维护规范 (docs/AGENTS.md)

本文件是 `docs/` 目录及其所有子目录下文档编写、修订与审查的专门规范。本文件服从项目根目录 `AGENTS.md`。同类型规范如有冲突，以根目录 `AGENTS.md` 为准。

---

## 1. 语言连贯、自然、有逻辑

1. **真实达意，逻辑严密**：
   - 每句话必须表达具体的工程或设计意图，前后因果关系明确，段落衔接自然。
   - 杜绝缺少主语的长难句、欧化倒装句和代词指代不清（如指代不明的“它”、“其”、“这”）。
2. **拒绝浓烈“AI味”与虚浮修辞**：
   - 严禁使用毫无实质信息的模板化连接词与过渡句，例如“值得注意的是”、“不可否认”、“总而言之”、“综上所述”、“不仅如此，更重要的是”、“众所周知”、“毋庸置疑”、“犹如/宛如”。
   - 严禁套用生硬的排比或论述模板（如多人物档案重复使用“XX的转折是从…走到…”句式）。人物性格与经历应结合具体事件自然叙述。
3. **剔除互联网大厂空洞黑话**：
   - 除实验评测中严谨的控制理论学术术语（如开环实验 `open-loop`、闭环仿真 `closed-loop`）外，严禁在工程交付与玩法描述中滥用“闭环”、“赋能”、“抓手”、“链路”、“打通”、“颗粒度”、“心智模型”、“底层逻辑”等互联网黑话。
   - 工程交付统一使用“端到端验证”、“全流程贯通”、“调用链”等具体技术词汇。

---

## 2. 标点符号规范（严禁“只要直角引号”）

1. **遵循国家标准 GB/T 15834―2011《标点符号用法》**：
   - 中文正文横排一律采用规范的标准弯双引号 `“……”`（外层）和弯单引号 `‘……’`（内层嵌套）。
   - **严禁全篇机械套用日式/繁体直角引号 `「」` 与 `『』`**，坚决杜绝“只要直角引号”的不良风气。
2. **标点与 Markdown 标记各司其职**：
   - **直接引语与对话**：使用冒号与标准弯双引号，如 `岑雁在调令上签字，说：“他需要换个地方想清楚。”`
   - **实体、概念与专有名词**：在正文中直接使用中文词汇，必要时使用 Markdown 加粗 `**...**`，不得随手套用引号。
   - **状态、属性枚举与代码字段**：使用 Markdown 行内代码反引号 `` `...` ``，如 `` `materials_consumed` ``、`` `已实现` ``。
   - **法案、法律与书籍**：严格使用中文书名号《》，如《轮换供水法》、《配给透明法》，严禁套用引号。
3. **全库风格统一**：
   - 同一篇文档内严禁直角引号 `「」` 与弯双引号 `“”` 无序混杂打架。

---

## 3. 表述清晰与消除歧义

1. **机制规则必须定量可落地**：
   - 游戏规则与机制表述必须清晰明确，能直接对应到数据模型、状态机或测试断言。
   - 严禁用政治隐喻或模糊口语代替规则机制（例如不得只写“按规矩办让法案打七折”，必须明确是工期延长 30% 还是收益打七折）。
2. **术语全库一致**：
   - 严格遵守 `design/world/canon.md`（设定速查表）与 `00-scope-and-invariants.md`（序章切片与不变量）确立的唯一定义。
   - 派系、角色名称中英文映射必须准确，不得出现“瓦砾同盟”与“砾火同盟”、“地球联盟”与“地生共约”等同义词乱用。
   - `pnpm test` 核对内容包的派系 ID 和显示名，以及正式运行名册的 Agent ID 和显示名。
3. **杜绝中英生硬夹杂**：
   - 中文正文叙述中不得突兀夹杂未翻译的英文词汇（如不得写 `吞并 aggressiveness`，应写作 `吞并激进倾向`）。专有代码标识符（如 `agentId`、`tick`）一律使用行内代码反引号包裹。
4. **用锚点引用章节与验收用例。** 链接文字使用章节或用例名称。一组用例共用验收条件时，可以链接到该组标题。

---

## 4. 存疑与修改界限

1. **严禁静默修改原有业务意图与规则**：
   - 词句润色与用语修正不得改变文档原有的业务逻辑、数值初值、剧情事实与架构不变量。
2. **不确定时不猜，向用户报告决策**：
   - 凡涉及设计权衡、尚未定论的规则逻辑或发现前后文档存在矛盾且无法确定事实来源的，必须记录并向用户汇报，由用户裁决，不得自行武断决定。
