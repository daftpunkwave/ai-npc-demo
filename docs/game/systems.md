# 游戏职能模块与规则边界

> **设计权威（2026-11-20）：** 游戏设计意图见 [design/gameplay/11-agent-actions.md](../design/gameplay/11-agent-actions.md) 与 [14-agent-society.md](../design/gameplay/14-agent-society.md)。模块边界继续有效；与设计冲突时以 `docs/design/` 为准。

> 状态：目标设计。游戏只是全平台模块组合之一，地图、时钟、资源、行动、协议、通信、剧情与玩家授权均由可替换 provider 实现；宿主不固化这些游戏职能。本文只定义职能边界与不变量；首版的具体规则、数值与结算顺序见 [规则](rules.md)，初始数据见 [内容包](content-pack.md)，命令与事件见 [领域模型](../architecture/domain-model.md)。

## 1. 主体、接口与实现

基础宿主保留模块装配、生命周期、typed port 与事件通道、scope、版本/幂等/fencing 检查，以及不可绕过的提交协议。游戏具体规则与服务通过 ModuleDefinition 注册；一次运行组合为每项必需能力选择兼容实现。

低耦合优先：模块不 import 其他模块内部文件、不直接访问其状态表、不通过全局单例找依赖。需要协作时声明所需能力与 apiVersion，由组合根注入公开 port。模块内部按单一职责组织；不能通过把所有功能装进一个“高内聚游戏核心”规避可替换边界。

| 职能能力 | 输入与输出 | 可替换的内容 |
|---|---|---|
| game.clock | 运行模式与推进命令，输出持久 worldTick 与到期触发 | 实时映射、受控单步、暂停策略 |
| game.map | 授权地图、起终点、通行条件，输出路径与版本读集 | 地图表示、路径/通行判定策略 |
| game.resources | 只读资源状态、预留/消耗提案，输出变更计划 | 资源种类、配给与返还规则 |
| game.actions | 类型化行动、合法依赖结果，输出任务/后果计划 | 运输、护送、救援、修复等动作结算 |
| game.agreements | 条款、确认、履约事实，输出协议状态计划 | 提案、改约、履约与违约判定 |
| game.comms | 对话、消息、广播、证据分享，输出投递计划与知识授权 | 中继延迟、受众与传播规则 |
| game.scenario | 已发布事件卡、前置条件、时钟，输出合法局势命令 | 压力、触发、剧情推进策略 |
| platform.access-policy | 主体、目标、动作、当前授权，输出允许/拒绝与依据 | 玩家/派系/角色权限策略 |
| game.save / platform.storage | 一致恢复点、读写计划，输出存档与持久结果 | 存档编码、迁移与存储适配 |

这是职责清单，不代表所有能力必须各拆一个 npm 包。需要独立替换的功能应有独立能力/接口，即使首版由同一可信模块贡献多个相关 provider。模块 ID、能力、实现 ID 和版本由 [模块目录](../architecture/module-catalog.md) 与 [组合规范](../architecture/composition.md) 维护。

游戏规则 provider 只在 authority 打开的事务里通过 `WorldTx` 登记变更（相当于提交一份计划），不能自行提交数据库（[领域模型](../architecture/domain-model.md) 第 4 节）。ToolDefinition 经 command port 交给已注册的 handler 和 rules provider，最后由宿主提交关口写入，这条路径是唯一的世界写入路径。所有世界状态在一个正式 branch 中有唯一权威；换实现不产生平行权威。

## 2. 状态与人物认知

首版只实现支撑 NPC 行为的状态，不做完整商业 SLG 数值体系。地图节点/道路、通行/控制、有限资源、任务占用、伤势、协议、信息与局势卡分别由对应模块拥有 schema 和规则；公共事件及跨模块 DTO 归 contracts。

| 规则真值 | 主观层 |
|---|---|
| 物资实际剩余与占用 | 角色认为物资充足、信任谁负责配送 |
| 位置、行动与伤势 | 害怕再受伤、记得谁曾救援 |
| 已签条约、截止、结果 | 是否记得、是否愿意主动履约 |
| 消息发送/接收与公开记录 | 相信其内容、误读其意图 |

模块更换必须声明状态 schema、事件兼容性与迁移路径。memory/context 替换不允许顺带改变资源、合同或地图规则；若实验改变游戏规则，应改 moduleAssemblyRef，记录规则/内容版本并作为独立实验轴。

## 3. 时钟与地图的首版实现

单玩家默认使用“运行/暂停/单步推进”时钟 provider。运行时按部署配置将真实时间映射为 worldTick；实验采用受控逻辑 tick。暂停停止逻辑计时与新自主决策，在途结果通过 fencing 失效；聊天不自动跳过一个 turn。

离线默认暂停，不累计离线战争。恢复继续未完成任务与到期检查，不按现实离线天数追加记忆。真实网络耗时仅计性能，不参与记忆衰减。时钟实现可换，但持久 tick 不得倒退或绕过暂停协议。

地图模块提供版本化节点/道路内容，traversal provider 判定可达、通行条件和行程 tick。服务端裁决路径；客户端 renderer/camera/input 只是独立显示与交互模块，不能以精灵走到屏幕目标作为完成事实。

## 4. 轻资源与行动的首版实现

设计共有能源、材料、食物、供给、医疗、水六种资源；**序章只结算供给、能源、医疗三种库存**，材料、食物、水在 t168 按设计初值出现，不参与序章的预留、日耗与任务成本。情报以证据与授权表达，不作为可刷货币。UI 模块优先显示短缺/可维持/有余量和可执行事项，内部整数用于一致性。

提案、命令与任务分层：commandStatus=accepted/rejected 表示不可变受理结果；接受时可创建资源预留和任务。taskStatus 取 pending、running、completed、failed 或 cancelled；受阻以 failed 和 reasonCode 表达。工具的 executionStatus 与这些业务状态分开，见 [公共契约](../architecture/contracts.md)。

提案不占资源；接受时原子检查并预留。撤销按动作 provider 的显式补偿规则结算，不统一全额退款。冲突按提交顺序与 expectedVersions 裁决，玩家与 Agent 使用相同的已选规则组合。

首批行为为运输、护送、救援、修复与侦察五种任务；临时通行不是任务，而是协议条款 `grant-passage` 生效后产生的通行许可。战斗由规则模块抽象为道路风险、延误与伤势，不做战斗数值；随机结果使用注入随机源并记录种子。资源与行动模块共同返回一个可原子提交的计划，不能各自先扣资源再等待别的模块补写。

## 5. 角色意愿与关系

能做、获准做、愿意做分别判断：技能/位置/伤势归状态与规则，权限归 access-policy，意愿归 decision provider。拒绝可因危险、职责、经历或价值观，必须有当前情境或可定位来源。

关系可由 memory 策略维护信任、亲近、戒备等带原因账本；是否进入 decision 由子 profile 明确。世界规则不能秘密读取全历史账本替 Agent 决定所有意愿。

角色接受参与后登记任务和授权；其是否记得仍由 memory 决定。角色与派系分别拥有认知，派系意见经消息传达而非共享脑内状态。可替换职责/权限策略也不能通过一条角色台词临时授予系统能力。

## 6. 协议与信息

协议模块维护当事人、条款、到期、资源/通行条件、确认记录、履约事件与修订。双方确认前为提案；fulfilled/breached/blocked 是协议履约结果，不是 taskStatus。

规则到期只结算真实结果；主动提醒/提前履约来自本组启用的前瞻记忆或计划。不得给 M0 共用全合同提醒器。改约需新确认事件，模型不能直接覆盖旧条款。

非正式嘱托可进入前瞻记忆候选，不自动成为有资源担保的正式合同。InformationShared 保存来源、发送者、接收者、获知时间与传播范围；公开化需要新授权事件，不授予读取原始私聊或整库记忆的权限。

## 7. 剧情运营与扩展

game.scenario 接收策划发布内容，事件卡声明 ID/版本、条件、受众、允许命令、延时、次数限制、幂等键与补偿路径。草稿不进感知，发布后按条件产生合法命令；剧情模块不能直接宣告无规则支持的胜负。

三个非人类势力（巡裔、根庭、泊星者）可由 Agent 或真人运营，通过相同命令 port。服务端页面位于 http://127.0.0.1:3000/console/，玩家页面位于 http://127.0.0.1:5173；页面功能是可注册 UI 模块，不能因操作员能打开后台就获得全部真值或写库权限。两个端口是部署不变量，控制台不新开端口。

覆盖性调试产生 ScenarioOverride 与实验污染标记；历史修正用补偿事件。新增职能必须声明 capability、状态/schema 和参与的事务/投影，不把“临时剧情逻辑”塞进宿主或某个 NPC executor。

## 8. 安装、替换与卸载

RunSpec.moduleAssemblyRef 冻结整个游戏/Agent/平台/UI 组合，Agent profile 只是其中子配方。安装先校验依赖、接口版本与权限，再注册 handler、timer 和 UI 贡献；缺必需能力拒绝启动。

可选模块卸载时撤销它贡献的工具绑定、订阅、任务入口与 UI 槽；依赖它的消费者必须停用或显式降级，不得保留能点击却不会工作的操作。必需 provider 不能在活动组合中拔空：先停止组合或准备兼容替代，实现 drain/fence 和状态迁移后切换。

首版以暂停点的新 run/后继 branch 替换有状态模块，不承诺任意热拔。更换规则需要规则/schema 版本；更换存储需要一致性与恢复验证。具体生命周期见 [插件机制](../architecture/plugins.md)。

## 9. 验收

重复命令只预留一次；冲突资源只有合法一方成功；timer 与恢复不重复结算；暂停不推进 tick；角色拒绝不会被当成同意；误解不污染真值。

首版的替换演示固定为：剧情推进 provider 从 `game.scenario.watergate` 换成 `game.scenario.watergate-escalating`，客户端 HUD 从 `client.hud.standard` 换成 `client.hud.compact`，控制台观测页从 `console.observability.standard` 换成 `console.observability.lite`，再加上 memory 的四组切换。时钟 provider 的替换属于后续扩展，首版不要求。替换只改模块自身、注册清单与配置，不修改无关消费者源码；差异要有版本和 trace 记录，依赖与状态兼容性需经过验证。缺 provider 或不兼容版本必须在启用前失败。两端口启动、界面可用与最终验收见 [交付计划](../delivery/roadmap-and-acceptance.md)；模块目录见 [模块目录](../architecture/module-catalog.md)，事务恢复见 [事件与状态](../architecture/events-and-state.md)，行为复用见 [Tools](../agent/tools.md)。
